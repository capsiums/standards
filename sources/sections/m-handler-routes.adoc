[[module-handler-routes]]
== Module: Handler routes

The handler routes module extends resource routing with dynamic HTTP API
routes: routes that map a URL path and an HTTP method to an executable
handler file contained in the package. Where the core package serves only
static resources and datasets, a package claiming this module can ship API
endpoints whose responses are produced by code.

A reactor claiming this module executes the handler of a matching route. A
reactor that does not claim this module shall answer requests to handler
routes with `501 Not Implemented` (see the reactor annexes for examples of
this behavior).

=== Additional requirements

. A handler route in `routes.json` shall declare a `path`, an HTTP `method`,
and a `handler` that references a script file contained in the package.
. The `handler` path shall be package-relative and shall resolve to an
existing file in the package.
. A reactor claiming this module shall, on a request whose path and method
match a handler route, execute the referenced handler and deliver its
response to the client. The handler shall be an ECMAScript module whose
default export — or whose named `fetch` export — is a function of the
shape `(request: Request) => Response | Promise<Response>`.
. Requests to a handler route with an unsupported HTTP method shall be
answered with `405 Method Not Allowed` and an `Allow` header listing the
supported methods.
. Header responses declared for the route — inline in `routes.json` or
through external header files (<<route-headers>>) — shall be applied to the
handler's response.
. A failure to import the handler module, or a runtime failure during its
execution, shall be answered with `502 Bad Gateway`.
. A reactor without a JavaScript execution contract shall answer handler
routes with `501 Not Implemented`.

=== HTTP API routes in `routes.json`

The core `routes.json` file (Clause 5, Resource routing) maps URL paths to
resources; this module adds route entries that carry a `method` and a
`handler` instead of a `resource`.

Example `routes.json` with HTTP API routes::

[source,json]
----
{
    "index": "index.html",
    "routes": [
        {
            "path": "/api/v1/users",
            "method": "GET",
            "handler": "api/v1/users/getUsers.js"
        },
        {
            "path": "/api/v1/users",
            "method": "POST",
            "handler": "api/v1/users/createUser.js"
        },
        {
            "path": "/api/v1/users/:id",
            "method": "PUT",
            "handler": "api/v1/users/updateUser.js"
        },
        {
            "path": "/api/v1/users/:id",
            "method": "DELETE",
            "handler": "api/v1/users/deleteUser.js"
        }
    ]
}
----

In this example, the `routes.json` file defines dynamic HTTP API endpoints:
each route binds a path (with optional path parameters such as `:id`) and an
HTTP method to a handler script in the package, which is executed to produce
the response.

Handler routes participate in route visibility (`exported` / `private`,
<<route-visibility>>) like any other route, and can be inherited and
processed by dependent packages under the composite packages module
(<<module-composite>>); request headers supplanted with `requestHeaders`
are applied when the request is forwarded to the handler.

=== JavaScript handler contract

A handler is an ECMAScript module loaded from the package content. The
reactor imports the module and invokes its handler function for each
matching request:

[source,javascript]
----
// content/api/v1/hello.js
export default async function (request) {
  return new Response(JSON.stringify({ hello: "world" }), {
    status: 200,
    headers: { "Content-Type": "application/json" }
  });
}

// alternatively, a named "fetch" export:
export function fetch(request) {
  return new Response("OK");
}
----

The handler function receives a `Request` and returns a `Response` or a
`Promise` resolving to a `Response`, following the fetch handler contract
of the web platform. The reactor matches the route's declared HTTP `method`
before dispatching; a mismatch is answered `405 Method Not Allowed` with an
`Allow` header. A module that fails to import, or a handler that throws or
rejects, is answered `502 Bad Gateway`.

=== Sandbox enforcement

Handler code is package-supplied. A reactor claiming this module
SHALL execute handlers with least privilege as follows:

. *Opaque origin.* The handler module SHALL execute in a context
whose origin is opaque (an opaque origin per https://html.spec.whatwg.org/multipage/origin.html#concept-origin-opaque[HTML
§origin]). In practice this means a service worker (browser
reactors), a `data:`/`blob:` URL import (Node/Deno/Bun), or a
dedicated Worker / `child_process` (host reactors).

. *No extension APIs.* The handler SHALL NOT have access to the
host's extension or platform APIs (no `chrome.*`, no
`browser.*`, no `process.env`, no `Bun.*`, no `Deno.*` on
host reactors — except where the reactor's deployment
documentation explicitly grants a capability).

. *CSP profile.* A browser reactor SHALL apply a restrictive
Content Security Policy to the handler context: minimum
`default-src 'self'`, no `'unsafe-eval'`, no `'unsafe-inline'`
for scripts. `connect-src` MAY be opened to external hosts
when the package's `metadata.json` declares them under
`handler.allowConnectSrc` (a string array); otherwise
`connect-src 'self'`.

. *Capability grant.* A reactor MAY grant additional capabilities
beyond the defaults (e.g. filesystem read of one directory) when
the package's `metadata.json` declares them under
`handler.capabilities` (an array of capability tokens defined in
<<handler-capabilities>>). Granting a capability not declared in
the package is non-conformant.

. *No sandbox, no execution.* A reactor that cannot satisfy
requirements 1–3 above SHALL NOT attempt to execute handlers
and SHALL answer every handler route with `501 Not Implemented`,
exactly as a reactor that does not claim this module.

[[handler-capabilities]]
==== Declared capabilities

The `handler.capabilities` field in `metadata.json` MAY name
additional capabilities the package requests. Recognized tokens:

* `"fetch:external"` — open `connect-src` to any origin.
* `"fetch:<host>"` — open `connect-src` to one specific host
  (e.g. `"fetch:api.github.com"`).
* `"storage:opfs"` — read/write access to Origin Private File
  System (browser reactors only).

A reactor SHALL ignore capability tokens it does not recognize
(silent no-op), and SHALL document in its README which tokens
it grants.
